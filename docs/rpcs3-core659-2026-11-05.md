# RPCS3 Core 659 : soumissions anticipées aux frontières de passe (Assassin's Creed, Black Ops II) et compteurs ZCULL, 5 novembre 2026

Core 659 = Core 655 ([fiche](rpcs3-core655-2026-11-04.md)) + [`build-utils/rpcs3/core659-from-655.patch`](../build-utils/rpcs3/core659-from-655.patch),
replié dans le delta canonique (`core659_20261105`, [`core659-delta.json`](../build-utils/rpcs3/core659-delta.json)). Même dépendance
MoltenVK que le Core 655. ABI 30, 92 exports et identités codegen inchangés : aucun cache PPU ou SPU n'est invalidé.

Entrée : les journaux privés de l'IPA 657 (Core 655, PID 10471 ; [analyse](rpcs3-ipa657-logs-2026-11-05.md)). Les chiffres
ci-dessous sont **mesurés** (champ du journal), **dérivés** (calcul sur des champs mesurés) ou issus d'un **modèle hôte**, ce qui
est toujours dit. Aucun n'est un gain observé sur iPhone.

## 1. Assassin's Creed : où passe le temps d'une image

**Chronologie mesurée (fenêtres 1:25 à 1:42) :**

- Le GPU est inactif 8,7 à 13,0 ms par image (23 à 32 % de l'intervalle ; 1:42 : 12,0 ms sur 42,6 ms, GPU occupé 30,5 ms).
  Dérivé de `GPUTIME621 busy_ms` et de `FRAMEPROF527 total_interval_ms`.
- Chaque command buffer autre que celui du flip est un vidage demandé par ZCULL. L'identité `queue_submits = images +
  hint_flushes` tient dans les six fenêtres (1:42 : 344 = 118 + 226).
- Le jeu attend chaque rapport ZCULL jusqu'à la fin **du command buffer entier** qui contient sa requête. MoltenVK ne
  publie un résultat d'occlusion qu'à la fin du `MTLCommandBuffer` (`MVKCommandBuffer.mm:1328-1338` → `MVKQueryPool.mm:55-62`).
  Les chiffres de 1:42 :
  - attente du jeu : 32,0 ms par image, pour 30,5 ms de GPU (`ZCULLDEMAND619 waits=259:3779.8:43.65`) ;
  - prise en charge et service du rapport : 4,7 ms seulement par image (`pickup=246:321.4`, `service=246:235.6`) ;
  - le reste est l'exécution GPU du command buffer.
- Pendant l'attente, le RSX n'enregistre rien. Le jeu reprend ensuite et enregistre la suite de l'image **pendant que le GPU
  n'a rien en file**.
- Inactivité GPU par image = temps d'enregistrement RSX échantillonné (`RSXFRAME551` setup + vertex + texture + exec +
  flip) + un délai de remise de 2,1 à 3,6 ms. L'égalité tient à ±0,7 ms dans 4 fenêtres sur 6 ; dans les deux autres il
  reste 2,3 ms (1:40) et 4,3 ms (1:39, deux images limitées par le CPU invité). Enregistrement et exécution ne se
  recouvrent pas.
- Ni contre-pression ni attente de fence : `RSXSYNC551 frame_cleanup`, `hard_sync` et `cb_reuse` valent 0. Le seul couplage
  CPU-GPU est la lecture des rapports ZCULL.
- Image longue 6776 (59,66 ms) = 3,17 ms de délai + 39,93 ms de GPU de l'image précédente (jeu bloqué) + 16,56 ms de queue
  CPU avec le GPU inactif.
- 26 images sur 118 dépassent 33 ms de GPU seul : celles-là resteraient au-dessus de 30 FPS même avec un recouvrement parfait.

**Le levier existant n'est pas actif pour ce titre.** La soumission anticipée 561 envoie, en fin de draw, les draws déjà
enregistrés quand le GPU a tout terminé. Elle est automatique pour Dragon Ball Z (+1,8 FPS médians, 12 paires A/B sur 12,
[`rpcs3-cell585.md`](rpcs3-cell585.md)) et God of War III, mais pas pour Assassin's Creed : `OPT561 early_submits=0`. Telle
quelle, elle aurait un coût sur ce titre : en fin de draw la passe de ce draw est ouverte, et la soumission la ferme. Le draw
suivant sur la même cible stocke puis recharge alors tous les attachements.

## 2. Le changement

**`REWINDBOX_EARLY_SUBMIT_BOUNDARY_659`** (`IOSEarlySubmit.h`, `IOSTitleLevers.h`, `VKGSRender.cpp/.h`, `VKDraw.cpp`, politique,
réglage, `COREPROF OPT561`) :

- Le mode automatique de 561 inclut Assassin's Creed (`BLES00158`, `BLUS30089`) et Black Ops II (`BLES01717`), en **mode
  frontière** :
  - une soumission décidée en fin de draw (GPU vidé, 32 draws au moins, 6 par image au plus : règles de 561 inchangées) est
    **armée** ;
  - elle est prise au début d'un draw suivant, ou juste après la préparation de ses textures, **si aucune passe n'est
    ouverte** à ce point : la passe a été fermée par une copie, une transition ou une méthode entre deux draws ;
  - sans un tel point, elle est prise en fin de draw après 32 draws de plus (repli, comme 561) ;
  - toute autre soumission principale (flip, vidage ZCULL, demande de vidage) emporte les draws armés et désarme.
- Commandes, ordre et synchronisation inchangés : seule la frontière du command buffer bouge. Les requêtes d'occlusion
  ouvertes sont closes puis reprises dans le command buffer suivant, comme à toute soumission, et leur somme est exacte.
- Au point « après textures », rien du draw n'est encore lié : les sous-ressources temporaires sont créées et libérées
  après, dans la portée de la soumission suivante. Avec l'ordonnanceur de calcul asynchrone en mode « device », ce point
  n'est jamais utilisé : l'attente GPU qu'il enregistre reste avec le draw. Le mode par défaut est « safe » (hôte).
- Dragon Ball Z et God of War III gardent la soumission en fin de draw. « Activé » sur un autre titre aussi.
- `COREPROF OPT561` ajoute `at_pass_boundary`, `armed`, `boundary_starts`, `boundary_textures`, `fallback_submits`,
  `disarmed` et `max_deferred_draws`. Au démarrage : ligne `Resolved title policy 659`.

**`REWINDBOX_ZCULL_READ_LEAD_659`** (compteurs seulement) : chaque tranche de rapport d'une page ZCULL verrouillée note quand
son rapport en attente le plus ancien a été mis en file. Chaque accès du jeu qui trouve sa tranche en attente ajoute cet âge,
une fois par faute. Ligne `COREPROF ZCULLLEAD659 leads=nombre:total_ms:max_ms leads_over_15ms=N`. Cette mesure décide du
levier suivant (§5).

**`REWINDBOX_ZCULL_HINT_SITES_659`** (compteurs seulement) : chaque vidage demandé par ZCULL est compté par site d'origine
(`sync`, `update` profondeur de file, `update` âge critique, `read_barrier`, `ios_service_read`). Ligne `COREPROF ZCULLHINT659`.
Cette mesure confirme ou réfute la cause des images de Black Ops II à environ 140 soumissions (§4).

**Modèle hôte** (pas une mesure) : 5,9 µs d'enregistrement et 20 µs de GPU par draw, remise de 1,4 ms + 1,07 µs par draw du
command buffer, deux lectures ZCULL par image qui attendent leur command buffer.

- Image moyenne : 48,3 ms sans soumission anticipée, 44,9 ms avec 561 en fin de draw, 44,9 ms en mode frontière à
  16 draws, 44,7 ms à 32.
- Passes coupées par image : 7,0 (fin de draw) → 4,0 (frontière à 32).
- La fenêtre de 32 draws coûte au plus 0,3 ms par image si une coupure de passe coûte 0,1 ms. Elle fait gagner 1,1 ms si
  une coupure coûte 0,5 ms.
- Une règle « un envoi en vol » ne gagne que 0,3 ms de plus (44,3 ms) pour 70 % de coupures en plus : elle n'est pas retenue.
- Le modèle montre aussi la limite restante : chaque lecture ZCULL vide le GPU, donc il reste au moins une remise par
  lecture.

## 4. Black Ops II

- **Débit.** En 3:16, la GPU n'est occupée que 25 à 35 % du temps. Les attentes ZCULL du jeu font 107 pour 1 566,5 ms, dont
  2,1 ms de prise en charge et de service par attente ; il reste 12,5 ms par attente (dérivé) pour l'aller-retour GPU.
  Le mode frontière s'applique aussi à ce titre.
- **Images à ~140 soumissions** (3:12-3:13 : `hint_flushes` 2 844 et 2 861 par fenêtre). Cause **inférée** par élimination :
  le seuil de profondeur de file de `ZCULL_control::update` (`RSXZCULL.cpp:628-645`, 1 792 tâches, identique en amont). Rien
  n'est changé avant que `ZCULLHINT659` l'ait confirmé.
- **Image de 985 ms (3491)** : non attribuée. Le FIFO RSX est resté vide environ 985 ms (échantillon hôte `rsx=0.0` sur une
  fenêtre de chargement qui couvre le blocage). Le CPU est à 63 %, aucune attente ZCULL au-delà de 23,2 ms, aucun pipeline
  bloquant. Les candidats :
  - (a) un épisode transitoire du même défaut de mise à jour perdue qu'au gel, en réservations relâchées (le plus cohérent) ;
  - (b) un à-coup propre au jeu ;
  - (c) une construction SPU sur une tâche critique, bornée à 308 ms.

  **Test qui les sépare** : même session multijoueur avec le profil `9403a7bf` (réservations précises et préchauffage)
  pendant au moins 10 minutes, en comptant les images de plus de 500 ms et les `FREEZE_EPISODE`. Si le spin de
  `0x73d1e8` / `0x2e208a0` réapparaît, c'est (a). Si ces images disparaissent avec les réservations précises, c'est aussi
  (a). Si elles persistent avec tous les threads en attente de sémaphore ou d'E/S, c'est (b).

## 5. Pistes examinées et non retenues dans ce Core (raison démontrée)

**Coût du chargement SPU** (2:5 : 8 793 blocs, tous dans le cache d'objets ; 0,181 ms de chargement d'objet, 0,193 ms de
construction et 0,031 ms de lecture par bloc ; 26,0 Mo d'objets, environ 2,95 Ko par bloc) :

- Sur un succès de cache, l'IR LLVM est reconstruit en entier (`SPULLVMRecompiler.cpp:4396-4400`). L'objet est lié par deux
  appels LLVM « récupérables », chacun confié à un thread du pool iOS (`JITLLVM.cpp:1606` et `:1764` ;
  `Thread.cpp:2928-2975`).
- Éviter l'IR est faisable : la clé du cache est connue avant l'IR, et un prototype de chargement sans module existe,
  inutilisé (`JITMinimalObject.h`). Il faut lier exactement les symboles d'aide et les patchpoints `-pp-N`.
- Fusionner les deux appels ferait économiser un passage de travail au pool par bloc.
- **Les deux touchent des entrées codegen** (`JITLLVM.cpp`, `JIT.h`, `SPULLVMRecompiler.cpp` figurent dans
  `NEOSTATION_SPU_CODEGEN_SOURCE`). Sans alias exact et audité (précédent du Core 627), chaque appareil recompilerait à froid
  tous ses modules PPU et objets SPU. Le chargement sans IR demande en outre un banc qui exécute le vrai recompilateur SPU,
  absent ici.
- Prochain lot dédié : alias exact, table de symboles stricte qui retombe sur l'IR à la moindre inconnue, comparaison des
  objets et des pointeurs sur un corpus.

**Préchauffage SPU de Black Ops II** (`9403a7bf`, 2 workers sur iOS, `SPUWarmupPolicy.h:51-57`) — arbitrage **estimé, non
mesuré** :

- Démarrage : environ 8 800 blocs × 0,405 ms ÷ 2 ≈ 1,8 s de plus. Le coût par bloc observé au démarrage est plus élevé
  (construction 0,52 à 0,58 ms, lecture 0,40 à 0,45 ms) : jusqu'à environ 4 s.
- Transition : 3,3 à 3,5 s de temps SPU en moins, et des images de 0,8 à 1,3 s en moins.
- Mémoire : les mêmes ~26 Mo d'objets, chargés au démarrage au lieu de la transition, plus les programmes du cache jamais
  utilisés dans la session (part inconnue).
- Les lignes `SPUWARMUP begin/end` (`SPUCommonRecompiler.cpp:1535, 1906` : programmes, `elapsed_ms`) le mesureront.

**Coût des textures d'Assassin's Creed** (`texture_ms` 5,03 ms par image en 1:42, 2,19 ms en 1:25) :

- `upload_calls` compte chaque recherche d'échantillonneur, succès inclus (`texture_cache.h:3526`) : 904 par image.
  `upload_misses` compte les envois CPU : 29 dans la fenêtre.
- L'étape inclut aussi `bind_texture_env` pour les 1 515 draws, soit environ 3,3 µs par draw.
- L'époque de validation, active pour ce titre, évite le hachage. Elle avance à chaque changement de PUT
  (`RSXFIFO.cpp:168-172`) : 15,7 fois par image.
- Une mémoïsation par slot est possible, mais seulement avec une nouvelle génération d'invalidation des écritures RSX
  ciblées, qui n'existe pas. Sans elle, une texture périmée s'afficherait. Non fait.

**Fins de passe restantes** (1:42) :

- `image_helpers.cpp:96` : 3 008 fins, transitions vers des dispositions de copie ou de cible suivante. Elles sont
  nécessaires, car Vulkan n'enregistre pas de copie dans une passe ; le Core 655 garde déjà les 236 transitions de lecture.
- `barriers.cpp:95` : 638 fins, boucles de retour en GENERAL ; MoltenVK redémarrerait l'encodeur de toute façon.
- `VKDraw.cpp:229` : 226 fins, des soumissions ; seulement 13 reprennent la même cible.
- Le Core 659 n'en ajoute pas de nouvelles. Une attribution par ressource demanderait d'étendre le recensement.

**Pointe de 1:30** : deux nouveaux programmes de fragments, compilés de façon bloquante en Metal (1 038 ms, dont 676 ms pour
un seul). Ils sont ajoutés au cache (`cache_additions=2`, 612 pipelines vivants), donc préconstruits au prochain démarrage.
C'est un premier usage, pas un coût récurrent.

**Soumettre le command buffer dès le rapport ZCULL** (levier suivant) : la requête serait déjà exécutée quand le jeu la lit.
Son gain dépend de l'avance entre rapport et lecture, que mesure `ZCULLLEAD659`. Si cette avance dépasse la remise plus le GPU
de la requête, l'attente disparaît.

**Amont** (RPCS3 `eac8790`, MoltenVK `5189f8d`) :

- Pas de soumission anticipée.
- Le vidage des rapports critiques après 300 µs existe (`RSXZCULL.cpp:675-681`) mais reste inactif en mode à la demande iOS.
- Même seuil de profondeur de file.
- Même publication des requêtes à la fin du command buffer.
- Pas de saut d'IR SPU.
- Pas de chemin rapide de textures plus récent : l'amont protège les pages et ne hache pas.

## 6. Protocole de mesure sur iPhone

**Assassin's Creed** : même scène que les fenêtres 1:38 à 1:42, même état thermique au départ. Pour une paire A/B dans une
même session, alterner « Early command buffer submission » Automatique/Désactivé. Relever :

- `OPT561` : `early_submits`, `armed`, `boundary_starts` / `boundary_textures` / `fallback_submits` ;
- `GPUTIME621 busy_share`, visé au-dessus de 0,71 ;
- `FRAMEPROF527` : médiane, p95, p99 ;
- `ZCULLDEMAND619` : attente par image ;
- `RPASS652 same_target`, qui doit rester stable ;
- `frames_gpu_over33ms` ;
- `ZCULLLEAD659`.

**Black Ops II** : le protocole du §4. Relever aussi `ZCULLHINT659` dans les fenêtres à beaucoup de soumissions, les lignes
`SPUWARMUP` et `spu_blocks` à la première transition.

Aucun gain de FPS n'est annoncé avant ces mesures.

# RewindBox launch: what blocks the first interactive screen (22 November 2026)

**Facts that shape the work**

- The database is `package:sqlite3`, called synchronously through FFI (`lib/data/datasources/sqlite_service.dart:101-135`).
- With Flutter 3.47 the platform and UI threads are merged (`UiRefreshRateEngineHook.m`).

Every SQL statement and every main-thread native call therefore freezes the startup animation and the interface.
The real interface is attached after a chain of about thirty awaited steps in `main()` (`lib/main.dart`). With
`scanOnStartup` (the default), the startup overlay also stays until the full ROM scan has finished
(`SqliteConfigProvider.isLoading`, `system_content.dart`).

**The user's app.log (67 launches)**

- **Lines carry no time**, so it measured nothing.
- **The frame probe started only in `AppScreen`.** Long frames before it were never logged.
- **The RetroAchievements game table was rebuilt on all 67 launches.**
- **About a third of the launches** showed one `UI long frame` of 340–609 ms, all in "waiting" (the thread was busy),
  when the content appeared.

## Changes (each its own commit, nothing the user sees or sets changes)

1. **Measurement.** `StartupTimeline` (`lib/services/startup_timeline.dart`) writes `Startup: <step> <ms> ms (t=<ms> ms)`:
   - each step before the interface;
   - the configuration sub-steps (`systems sync`, `RetroAchievements table`);
   - `startup ROM scan`, `content ready` and `interactive` (the overlay is gone).

   The FrameTiming probe now starts right after the logger.
2. **RetroAchievements table only when its seed changes.**
   - Before: every launch emptied `app_ra_game_list`, parsed the 6 MB `assets/data/ra_insert.sql` character by
     character and ran 17,819 inserts.
   - Now: a SHA-256 of the seed (computed off the UI isolate) and the row count are kept in `app_seed_fingerprints`.
     A new seed, a missing marker or a different row count rebuild the table as before.
   - Linux test harness, real seed and schema: first build 1,244 ms, next launch 90 ms with identical rows, an
     altered table is rebuilt identically.
3. **Systems sync only when it would write something.** At startup the sync is skipped when every one of these is
   exactly as recorded right after the last full sync:
   - the definition files (by content);
   - the app build and the platform;
   - every row the sync reads or writes: systems, folders, extensions, emulators, `user_emulator_config`, and the
     emulator columns of `user_roms`.

   Any difference runs the full sync, a user's emulator choice included. Checked in the harness on the real schema:
   - a second full sync rewrites the same content (only unreferenced AUTOINCREMENT ids change);
   - the skipped call returns the same 122 systems;
   - 4 simulated launches in a row skip with unchanged content;
   - a user change forces the sync.

   Full sync 424–521 ms there, skipped call about 200 ms.

The times above are Linux test-harness times in debug mode, **not iPhone measurements**.

## Not done, and why

- **Showing the library before the startup scan ends.** It would change what the user sees: games that appear or
  disappear after display, focus moving at the end of the scan.
- **Deferring the PS3 restore, the audio session, the RetroAchievements session and the achievement-translation
  host.** Each either changes an order the user can perceive (the PS3 list, the first sounds, the connected status)
  or saves only a few milliseconds.
- **Not yet attempted: the first grid build.** It runs synchronous `existsSync` calls per system card and a
  synchronous read of `aliases.json` (`system_card.dart:251-273`, `system_art_alias_table.dart:32-43`). These are
  the next candidates if `UI long frame` remains when the content appears.
- **Not attempted: running the database on its own isolate, and `dlopen` of DolphinCore.** Both are larger changes
  with more risk.

## Checking on the iPhone (app.log)

```bash
grep -E "Startup: |UI long frame|refresh skipped|sync skipped" app.log
```
```bash
awk '/Starting RewindBox/{n++} /Startup: (interactive|startup ROM scan|systems sync|RetroAchievements table)/{print "launch " n ": " $0} /UI long frame/{print "launch " n ": " $0}' app.log
```

**Expected on a normal launch.**

- `RetroAchievements database already current (… games): refresh skipped`.
- `Systems definitions and tables unchanged since the last sync (122 systems): sync skipped`. The first launch after
  an update rebuilds both, once.
- Low `Startup: RetroAchievements table` and `Startup: systems sync` times.
- `Startup: interactive at …` lower than on the first launch after the update, which still rebuilds.

**Reading long frames.** Long frames during the startup animation are now logged, which they never were before. Only
the ones logged at or after `content ready` compare with the earlier log.

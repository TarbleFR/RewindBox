## 2. Assassin's Creed : défaut ZCULL hérité du profil

**Constat sur l'appareil (Build 612, édition BLES00158).**

- Démarrage de 10:25:38 avec la valeur du profil :
  `CONFIG_LAYERS part=rsx title=BLES00158 relaxed_zcull=true precise_zpass=false`.
  Les torches scintillaient.
- Démarrage de 10:26:06 après « Précision ZCULL → Approximative » :
  `relaxed_zcull=false precise_zpass=false overrides=gpu.zcull_accuracy`. Le joueur constate que
  les torches et les lumières ne scintillent plus.
- Seule l'édition **BLES00158** a été essayée. **BLUS30089** est le même jeu et reçoit la même
  valeur, mais elle n'a pas été lancée sur l'appareil.

**Modification.**

- `lib/services/rpcs3_game_profile_service.dart` : le profil des deux éditions porte
  `gpu.zcull_accuracy = Approximate`.
- Cette valeur s'écrit en deux booléens RPCS3, `Accurate ZCULL stats: false` et
  `Relaxed ZCULL Sync: false`. C'est la table que le Core relit (`RPCS3IOSZcullAccuracy.h`).
- Les deux booléens remplacent sur place le `Relaxed ZCULL Sync: true` de l'entrée officielle.

**Les quatre cas, tels que le code les traite.**

1. **Installation neuve.** La base de profils publiée avant chaque démarrage contient
   « Approximative » pour BLES00158 et BLUS30089. Elle est publiée par
   `publishDetectedProfilesForReadyRuntime`, de façon attendue, avant que le runtime soit prêt.
2. **Mise à jour d'une installation qui héritait de l'ancien profil.**
   - Le cache Core de la 612 contient encore `Relaxed ZCULL Sync: true`.
   - La publication remplace tout le fichier : `config_database::update` écrit le contenu
     complet de façon atomique, puis le publie.
   - La valeur du titre s'applique aussi par-dessus une entrée officielle rafraîchie depuis le
     réseau.
3. **Choix manuel explicite.** La couche `custom_configs/overrides/<JEU>.yml` s'applique après la
   base de profils (`System.cpp`). Le choix est donc conservé.
4. **Retour à « Valeur du profil » (`@inherit`).** Cette commande retire la seule clé
   `gpu.zcull_accuracy`. La base de profils redonne alors « Approximative ».

**Ce qui ne change pas.**

- Une ancienne configuration personnalisée complète (`config_<JEU>.yml`) reste prioritaire. La
  base de profils remplit seulement les réglages que cette configuration laisse à la valeur
  globale.
- Les autres jeux gardent leur propre défaut : BLES01717 garde `Relaxed ZCULL Sync: false`,
  BCAS20066 garde `true`, et les titres sans entrée n'ont pas de ZCULL.

**Tests hôtes.** Dans `test/rpcs3_game_profile_service_test.dart` :
- la charge utile des deux éditions ;
- le remplacement sur place d'une base relâchée ;
- la table Précise / Approximative / Relâchée ;
- le refus d'une valeur inconnue ;
- les défauts inchangés des autres jeux.

**Non vérifié sans iPhone.** La valeur native après un vrai redémarrage
(`CONFIG_LAYERS part=rsx`) se lit dans les prochains journaux : voir le protocole, section 6.

## 3. Assassin's Creed : performances en Approximative

**Mesures actuelles (612, session 2, 10:26:12–10:29:05, Approximative, `mvk_async=1` pendant toutes
les fenêtres).**

- **Scène lourde (10:27:29–10:29:00).**
  - 13 à 19 images/s, intervalle médian de 54 à 77 ms.
  - Le nombre de draws par image fixe la cadence : environ 1 370 draws donnent 54 ms, et 2 200 à
    2 700 draws donnent 70 à 76 ms. Cela fait 30 à 40 µs par draw.
- **Thread RSX.**
  - La FIFO est occupée 99 à 99,4 % de chaque fenêtre.
  - Le thread ne passe pourtant que 11 à 19 ms par image sur le CPU, soit environ un quart du temps.
- **Ce qui ne limite pas.**
  - Les SPU attendent un événement 26,6 s sur les 30 s de chaque fenêtre (6 threads) : ils sont
    inactifs environ 89 % du temps.
  - Le PPU utilise environ 11 ms par image.
  - Verrous de plage : 85 à 120 ms par fenêtre de 5 s. `wl_putllc` : 30 ms.
  - Soumissions Metal (`vkQueueSubmit`) : 20 à 25 ms par fenêtre. Présentation : 0,4 ms.
    Acquisition du drawable : 1,1 ms.
  - Attentes de fence (tous sites) : 0. Compilations Metal et LLVM : 0.
- **Réglages réellement appliqués.** `accurate_res=false`, `async_tex=false`, `mt_rsx=true`
  (`CONFIG_LAYERS`), `mvk_async=1` (RSXSYNC551, même source que `OPT587 mvk_async=`).

**Mesure ancienne, autre scène, ne pas mélanger.** Build 597, avec le ZCULL relâché du profil
d'alors : 27,9 images/s et un thread RSX à 1,0 cœur CPU.

**Ce que cela démontre, et ce qui reste à démontrer.**
- **Démontré.** En Approximative, le thread RSX est bloqué hors CPU environ les trois quarts de
  chaque image. Le temps par image suit le nombre de command buffers soumis : environ 32 par image
  dans la scène lourde, soit environ 2,2 ms chacun.
- **Pas encore démontré.** Le chemin de lecture d'un rapport ZCULL est le seul candidat que le
  code met en évidence : il soumet le command buffer ouvert puis dort dans MoltenVK
  (`vkGetQueryPoolResults` avec `VK_QUERY_RESULT_WAIT_BIT`). Aucun compteur existant ne mesure
  cette attente.

**Modification (mesure seulement).**
- La sonde `COREPROF ZCULLSYNC613` (`REWINDBOX_ZCULL_SYNC_PROBE_613`) donne par fenêtre :
  - le nombre et la durée totale et maximale des lectures de rapports ZCULL, soumission et attente
    MoltenVK comprises ;
  - les lectures qui ont dû soumettre ;
  - les soumissions anticipées `zcull_sync` ;
  - `precise` et `relaxed`.
- La timeline en garde une copie (`zcull_sync`).
- Retirer la sonde redonne les fichiers du Core 612 octet pour octet
  (`test/rpcs3_zcull_sync_probe613_test.py`).

**Aucun correctif de performance AC dans ce lot.** Si la sonde montre que les lectures ZCULL
représentent la majorité des ~55 ms, le correctif suivant visera ces allers-retours GPU, sans
revenir au mode relâché. Le gain d'images/s reste à établir.

## 4. Black Ops II (BLES01717)

### 4.1 Saccades en partie

**Mesures actuelles (612).**

- **Gel d'entrée, à chaque démarrage, au même point du jeu.** L'entrée dans le niveau ou dans le
  match reconstruit 5 000 à 6 500 blocs SPU en une fenêtre de 5 s. Ensuite, chaque fenêtre de jeu
  en reconstruit encore 400 à 2 500.
- **Ces blocs ne sont pas compilés.** Dans la fenêtre de 10:33:48 (session 10), on compte
  6 376 hits du cache d'objets SPU et 0 miss (SPUPROF, JITPROF `spu_codegen=0`).
- **Ils sont pourtant passés un par un.**
  - Ils traversent l'admission de compilation LLVM, qui réserve au moins 128 Mio par tâche,
    accepte au plus 3 tâches, et une seule sous pression mémoire ou thermique.
  - JITMEM indique `active_peak=1`.
  - WAITPROF527 indique `llvm_budget_cv` = 4 056 attentes, 10,8 s cumulées.
  - JITPROF indique `spu_cache_read` = 2,8 s de lectures d'objets et `spu_object_load` = 0,44 s
    d'éditions de liens.
- **Résultat à l'écran.**
  - Une image de 2,9 à 4,6 s à l'entrée de chaque niveau ou match. C'est le « gel » de l'entrée
    en multijoueur avec bots.
  - En jeu, des pics de 0,3 à 1,7 s dans les fenêtres qui reconstruisent des blocs.
  - Les fenêtres sans reconstruction restent sous 70–101 ms au maximum.
- **Pourquoi « à chaud » ne règle rien.** Le runtime SPU repart vide à chaque démarrage, et le
  disque est déjà chaud (hits). Le travail qui se répète est donc la reconstruction de chaque bloc
  depuis le cache d'objets, et non la compilation.
- **Réservations SPU.** `accurate_res=false` est effectif (`CONFIG_LAYERS`). En jeu, `wl_putllc`
  vaut 0, `putllc_heavy` vaut 0 et le temps de verrou de plage vaut 0 ms. Le coût restant est nul.
- **Référence 612, mesurée sur les présentations individuelles** (histogrammes FRAMEPROF527).
  Match multijoueur avec bots, session 13, premier passage après démarrage, 10:37:48–10:38:40 :
  - 29,4 images/s médianes ;
  - p95 de 67 ms, p99 de 288 ms ;
  - 164 images de plus de 50 ms et 26 de plus de 100 ms ;
  - maximum de 4,56 s.

  Aucun second passage dans le même processus n'existe dans ces journaux.

**Modification : `REWINDBOX_SPU_OBJECT_HIT_ADMISSION_613` (`SPULLVMRecompiler.cpp`).**

- L'objet est lu et validé avant l'admission.
- Un hit d'un bloc de 16 Kio au plus ne prend plus l'admission.
- Un miss, un objet rejeté ou un bloc plus grand sont admis comme avant.
- Le bloc est toujours construit par le thread SPU qui en a besoin, avant de l'exécuter : pas de
  compilation différée, pas d'interpréteur.
- Un alias exact dans `JITCacheCompatibility.cmake` garde les identités PPU `a987639e9f838d1c`
  et SPU `477a3fa442d27917`. Les objets émis ne changent pas et les caches existants restent
  valides.

**Résultat attendu, à mesurer.** Les hits ne sont plus sérialisés, ce qui doit raccourcir le gel
d'entrée et les pics. Un passage à chaud dans le même processus ne doit presque plus reconstruire
de bloc.

# RPCS3 Core 660 : décrémenteur SPU, chargement SPU sans IR, mémo des textures et leviers ZCULL, 5 novembre 2026

Core 660 = Core 659 ([fiche](rpcs3-core659-2026-11-05.md)) + [`build-utils/rpcs3/core660-from-659.patch`](../build-utils/rpcs3/core660-from-659.patch),
replié dans le delta canonique (`core660_20261105`, [`core660-delta.json`](../build-utils/rpcs3/core660-delta.json)). L'incrément est
fait de cinq étapes relues séparément, gardées chacune comme patch dans [`build-utils/rpcs3/core660-lots/`](../build-utils/rpcs3/core660-lots/) et
appliquées dans cet ordre : décrémenteur SPU, chargement SPU direct, mémo des textures, ZCULL, page de test. Même dépendance MoltenVK
que le Core 655. ABI 30, 92 exports, identités codegen PPU `a987639e9f838d1c` / SPU `477a3fa442d27917` inchangées : aucun cache
PPU ou SPU n'est invalidé.

Demande du mainteneur (5 novembre) : tous les correctifs identifiés et non encore implémentés entrent dans la prochaine IPA. Entrée :
les journaux privés de l'IPA 657 (Core 655, PID 10471) et l'analyse du Core 659. Les chiffres sont **mesurés** (journal), **dérivés**
ou issus d'un **modèle hôte**, ce qui est toujours dit. Aucun n'est un gain observé sur iPhone.

## 1. Les cinq étapes

### 1.1 Décrémenteur SPU (`REWINDBOX_SPU_TIMEBASE_MAPPING_660`)

- **Défaut, depuis le Build 481** : les blocs SPU LLVM qui lisent le décrémenteur chargent le décalage de base de temps par le symbole
  externe `spu_timebase_offs`. Il était lié à `g_timebase_offs` une seule fois, dans `init()`. Mais `compile()` efface toutes les liaisons
  avant chaque module (`clearAllGlobalMappings`) : le nom ne se résolvait plus, et `MemoryManager2::findSymbol` (`JITLLVM.cpp`) rendait
  un talon `make_null_function`. Le bloc lisait donc 8 octets du code de ce talon comme décalage : le décrémenteur JIT différait de la
  lecture C++ de `spu_thread` d'une constante propre à chaque démarrage. Effet sur les jeux non mesuré.
- **Correctif** : l'émetteur RdDec lie le nom à nouveau, juste avant sa lecture, pour le module en construction ; le chargement direct
  (1.2) le lie par sa table. L'IR et les objets émis sont inchangés.
- **Preuve** : `test/rpcs3_spu_timebase_mapping660_test.py` vérifie l'ordre dans les vrais fichiers 660 et 659, puis exécute une
  démonstration MCJIT sur les libLLVM 1, 18 et 20 de l'hôte : après l'effacement, le nom lu donne le leurre `0xdec0de` (comportement
  659) ; lié à nouveau, la vraie cellule (comportement 660).

### 1.2 Chargement SPU sans reconstruire l'IR (`REWINDBOX_SPU_DIRECT_OBJECT_HIT_660`)

- **Coût visé** (IPA 657, BO2, 2:5) : 8 793 blocs SPU à la transition, tous trouvés dans le cache d'objets, mais leur IR LLVM était
  reconstruit en entier avant de lier l'objet (0,193 ms de construction par bloc, mesuré) ; l'objet était lié par deux appels LLVM
  récupérables, deux passages par le pool de threads iOS.
- **Changement** : un objet du cache dont tous les symboles non définis sont des noms connus est lié sans IR.
  - La table de liaison (27 noms) est **générée** à partir des 46 sites `call()` et `updateGlobalMapping()` du traducteur ; le test la
    régénère et la compare.
  - Les patchpoints `<hash>-pp-N` sont régénérés strictement (zéros de tête, signes, autre module ou débordement refusés).
  - Tout autre cas (symbole inconnu comme `memcpy` ou les atomiques déportées, global absolu, doublon, définition étrangère, entrée
    absente, liaison nulle, copie impossible, refus de l'ajout) reprend le chemin IR **dans le même `compile()`**, sans erreur LLVM
    laissée et sans talon fabriqué. Les replis sont comptés par raison et journalisés (les 8 premiers par raison, puis 1 sur 256).
  - Ajout et finalisation dans **un seul** appel LLVM récupérable (un passage par le pool au lieu de deux).
  - L'entrée est résolue par `getFunctionAddress` (0 si absente), pas par `getPointerToNamedFunction`, qui ne rend jamais 0 ici.
  - La table est évaluée une fois par processus (`jit_runtime::alloc(0, 0)` prend un verrou global sur Apple).
  - Six lambdas du traducteur deviennent des fonctions statiques nommées, corps identiques à l'octet près, mêmes noms et arguments.
  - Publication identique au chemin IR. Réglage `experimental.spu_direct_object_hits`, Automatique = tous les titres.
- **Identités** : `SPULLVMRecompiler.cpp` et `JITLLVM.cpp` sont des entrées codegen ; deux alias exacts (`2a9548d2…` → `deb95e09…`,
  `a96b07eb…` → `001be95d…`) gardent les identités. Sans eux, elles deviendraient PPU `4ae735be5d408ae0` / SPU `adc211bccc359e89`.

### 1.3 Mémo des recherches de textures (`REWINDBOX_TEXTURE_LOOKUP_MEMO_660`)

- **Coût visé** (IPA 657, AC, 1:42) : 904 recherches de textures par image pour 1 515 draws, dont 61 % confirmées sans hachage parce
  que la section avait déjà été validée dans la même époque ; 5,03 ms d'étape texture par image échantillonnée (mesuré).
- **Changement** : par emplacement d'échantillonneur (4 voies), le résultat d'une recherche exacte est réutilisé pour une recherche
  identique (les six mots bruts du registre de texture, l'adresse résolue, les drapeaux vertex/BX2) tant que rien de ce qu'elle a lu n'a
  changé : même époque et même révision, aucune écriture ciblée sur sa plage, générations de sections et de contexte inchangées (tout
  écrivain d'un champ lu par la recherche les incrémente), aucune cible de rendu liée à l'adresse. Seules les vues directes en lecture
  de shader sont gardées ; un seul verrou de cache par recherche.
- **Vérification intégrée** : la **première réutilisation de chaque texture** d'une session, les 256 premières réutilisations, puis une
  sur 64 refont la recherche complète et comparent ; au moindre écart, le mémo se coupe jusqu'au prochain démarrage. C'est un contrôle,
  pas une borne : la justesse repose sur le recensement des écrivains, vérifié par le test.
- Portée : Assassin's Creed servi ; Black Ops II en vérification complète (chaque réutilisation refait la recherche : mesure seule).
  Réglage `experimental.texture_lookup_memo`.

### 1.4 Leviers ZCULL (`REWINDBOX_ZCULL_WATCHED_FLUSH_660`, `REWINDBOX_ZCULL_DEPTH_GUARD_660`)

- **Vidage anticipé des rapports attendus, Assassin's Creed seulement.** Mesuré (IPA 657, 1:42) : le jeu attend 32,0 ms par image ses
  rapports ZCULL, chaque attente couvrant tout le command buffer du rapport. Le Core apprend les emplacements que le jeu attend ; quand
  le rapport attendu est mis en file, la soumission « frontière » du Core 659 est armée pour son command buffer (sans couper de passe,
  6 soumissions anticipées et 2 soumissions surveillées par image au plus, repli après 32 draws). Valeurs, ordre et moment de lecture
  inchangés.
- **Garde de profondeur de file, Assassin's Creed et Black Ops II.** Mesuré (IPA 657, BO2, 3:12-3:13) : des images à environ 140
  soumissions, chaque nouveau rapport au-delà de 1 792 en file soumettant le command buffer ouvert. Le vidage n'est plus envoyé que si
  le command buffer ouvert contient la plus ancienne requête en attente, et au moins toutes les 256 vérifications (ses requêtes ne
  peuvent finir qu'une fois soumises) ; comportement amont au-delà de 8 192 rapports et après un basculement 619. Réglage dédié
  `experimental.zcull_depth_guard` pour l'essai A/B.

## 2. Ce que les six relectures ont changé

Deux relectures contradictoires par lot, chargées de réfuter, sur le vrai code.

| Lot | Verdict | Corrections apportées |
|---|---|---|
| Chargement SPU direct | réfuté (intégration, réalisme des tests), puis non réfuté | entrée par `getFunctionAddress` (la garde « entrée absente » devient réelle) ; table une fois par processus ; aucun talon avant la copie de l'objet (raison `copy_failed`) ; symbole fautif journalisé ; commentaires corrigés sur l'ordre de résolution réel de MCJIT (les définitions des objets chargés passent avant les liaisons) et garde statique : aucun nom de la table ni `-pp-` ne reçoit de corps ou de liaison interne dans le traducteur ; tests sur de vrais objets ELF aarch64 (`llc` 18), sur la vraie table compilée et sur le vrai corps de `try_add_minimal_object` ; appel unique |
| Mémo des textures | non réfuté ×2 | `dma_transfer` incrémente la génération si le pas change, et le recensement couvre les membres hors classe ; vérification de la première réutilisation de chaque texture ; compteurs remis à zéro par session ; `VKDraw.cpp` ne fait plus qu'**ajouter** des lignes (contrat du recensement livré `test/rpcs3_feedback_census_test.py`) ; contrôles statiques que la réutilisation restampe ses deux champs et repasse par la validation, et qu'aucun second verrou n'est pris, chacun avec sa mutation négative |
| Leviers ZCULL | réfuté ×2 | voir ci-dessous ; retrait de `-latomic` du test (absent de l'outillage Apple) ; garde active seulement si les lectures à la demande tournent vraiment ; un vidage sauté inscrit la requête soumise dans `m_sync_tag` ; scénario à plus de 2 048 requêtes en vol ajouté au test |

**Réfutation principale ZCULL** : avec plus de 2 048 rapports en vol par image, sauter les vidages épuise les 2 048 emplacements de
requêtes ; `allocate_new_query` lit alors le plus ancien rapport de façon synchrone (valeurs exactes, mais attente du RSX). Mesures sur
le **modèle hôte** des relecteurs, ms par image (référence = Core 659) :

| Scénario | Core 659 | garde d'origine | réserve de 256 emplacements | plafond 256 / command buffer (retenu) |
|---|---|---|---|---|
| 2 600 rapports par image, GPU saturé | 45,8 | 68,7 | 67,0 | 62,5 (garde seule : 53,4) |
| 4 000 rapports par image | 156,8 | 85,2 | 156,8 | 77,0 |
| file profonde (≈ 3 500 rapports) | 272,8 | 129,4 | 272,8 | 127,5 |
| BO2 type (pic 1 900) | 103,7 | 75,0 | 103,7 | 75,2 |

- La réserve d'emplacements libres est **écartée** : un rapport porte une requête, donc elle coupe la garde dès que la file atteint
  1 792.
- Le plafond par command buffer est **retenu** : meilleur que la garde d'origine partout, mais il reste une perte dans le premier
  scénario.
- Séparation des deux leviers sur ce scénario : le vidage surveillé seul donne 67,0 ms (la référence est 45,8). Il est donc retiré de
  Black Ops II, dont le modèle n'apprend d'ailleurs aucun emplacement.

## 3 bis. Compilation et pin

**Première demande** (run 41991624737 ; source `73933643`, demande `03874078`) : échec, sur deux points, sans aucun contrôle
retiré.

1. Job Core : la porte a refusé la dépendance MoltenVK du run 41912442196. Ce run avait enregistré l'ancien pont hôte
   (`Rpcs3InternalBridgePlugin.mm`), et le Core 660 a modifié ce pont (trois clés de la page de test). La garde est conservée. Une
   nouvelle dépendance est construite par le run 41993591512 (marqueur `5a514568`), avec la même source MoltenVK `db660224` et le
   même patch. Elle enregistre les entrées actuelles. `core-build.json` la déclare et garde comme remplacée celle du Core 610 de
   référence (run 41239096061).
2. Tests hôtes Apple : seule la commande `core660` a échoué. Le harnais du mémo de textures demandait `detect_leaks=1`, mais l'ASan
   d'Apple n'a pas de LeakSanitizer : le contrôle s'arrêtait (-6) avant le premier scénario. Cette option n'est plus demandée que
   sous Linux (`9889f711`), où elle reste active. Les 14 autres commandes Apple ont réussi (code 0), y compris l'étape SPU sous
   clang Apple avec les assainisseurs.

**Deuxième demande** (`4439519c`, run 41995875495, les deux jobs au premier essai) : réussie.

- Authentification de la fermeture des sources et de la dépendance (run 41993591512) réussie. `libMoltenVK.a` `d19d3a42…` est
  identique octet pour octet à celle des Cores 655 et 659, et les 11 entrées enregistrées sont égales à l'arbre.
- Tests hôtes Apple (clang Apple, macOS 15) : 15 commandes, toutes à 0, dont `core660` et `codegen-audit`
  (artefact 13401027264, `270758da…`).
- Core : artefact 13401208480 (`e633fd84…`, 29 369 639 o). `libRPCS3Core.dylib` fait 77 815 520 o (`1416a156…`), empreinte de charge
  utile `367a24cc…`, identité `rpcs3-ios-core660` (`e9497b41…`). Codegen PPU `a987639e9f838d1c` / SPU `477a3fa442d27917` inchangés.
  Tous les marqueurs sont présents (politique 660, COREPROF SPUDIRECT660, TEXMEMO660, ZCULLWATCH660 et ZCULLDEPTH660, les trois
  réglages).
- Les artefacts ont été téléchargés par les outils MCP de GitHub ; leurs empreintes sont égales à celles de l'API.
  `pin_errors` : vérifié ; bundle construit. Pin `f4c82c38…`.

Aucune mesure sur iPhone : aucun gain d'images par seconde n'est annoncé.

## 4. Limites

- Rien de `SPULLVMRecompiler.cpp` ni de `JITLLVM.cpp` n'a été compilé ici (pas d'en-têtes LLVM) : la compilation du Core est la
  première preuve. Le comportement de LLVM 22 (MCJIT) est déduit du code, vérifié seulement sur LLVM 18 et 20.
- Tous les chiffres de temps du §2 viennent d'un modèle hôte. Le scénario à 2 600 rapports par image reste moins bon que le Core 659
  avec la garde ; les journaux BO2 de l'IPA 657 montrent un pic d'environ 1 900, régime où le modèle gagne.
- Le mémo ne fait gagner que le corps de la recherche ; l'estimation pour AC est de 0,2 à 1 ms par image, non mesurée.

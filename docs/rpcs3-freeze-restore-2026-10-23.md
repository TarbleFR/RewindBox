# God of War III — Build 513 restore and freeze follow-up

The new internal iPhone logs show incomplete God of War III restorations. Investigation of the Build 513 source reproduces a restoration regression; the retained logs do not include its exact exception on the user’s save. The TAR worker probes once beyond an aligned member. That empty read calls `breathe(true)` again at the same position after the previous call removed the consumed prefix. If bytes from the next member were prefetched, the compressed reader attempts to discard unread data and fails `ar.pos >= ar.data_offset`.

The worker now stops at the declared chunk count. The 4 MiB iOS transfer ring and bounded decompression window remain. This does not change the save-state format, compatibility checks, user settings, save files or PPU/SPU object-cache namespaces. A real pinned ZSTD fixture reproduces the old failure and passes 20 corrected boundary/padding/next-member cases under ASan/UBSan. The original large-stream TAR fixtures still pass with the changed loop, including 257 MiB + 123 bytes. This establishes the source defect; the user's actual save-state payload was not supplied, so successful restoration of that file is not claimed.

The retained God of War III session falls from approximately 48–59 presented FPS to zero frames while process headroom remains about 3.6 GiB. RSX waits at 0x60300510 for 0x976 while observing 0x975, then the old recovery path incorrectly advances the FIFO after two seconds. No SPU compilation is recorded in these retained windows. Neither an LLVM/NEON bottleneck nor memory exhaustion explains this particular captured stall. The exact missing producer is not identified: the three earlier freeze dumps survive only as begin summaries, and the supplied previous NeoSwap generation ends before this later freeze. The successful save-state boot in the milestone file belongs to Bladestorm (BLES00113), not God of War III.

RSX now preserves the acquire dependency after the single recovery synchronization. Long waits leave CPU time to the producer through 100 microsecond waits after the first millisecond; service, pause and stop handling remain active. The timeout is reported once and a later real release is reported separately. Eight executable source-extracted scenarios pass, including a producer releasing after both old recovery windows and cancellation when no producer releases. The old implementation fails the delayed-producer negative control. This corrects unsafe FIFO progress and busy waiting; it is not proof that the underlying guest producer stall has disappeared.

A freeze is retained as one complete bounded milestone (at most 64 bounded records plus its wrapper, host cap 66 KiB), with one filesystem synchronization instead of a write per guest thread. Three executable snapshot cases verify complete begin/RSX/end records, the maximal thread count and the bound. TAR and VM restore phase boundaries are retained as milestones. Existing ABI 30, stop behavior, supported settings and unrelated engines remain unchanged.

Validation is targeted: source closure, real ZSTD and TAR fixtures, RSX scenarios, log admission/snapshot/ABI checks, existing ARM64/resilience contracts, and six compiler-command-preservation unit tests. Unchanged Core 513/510/508 evidence is authenticated and reused by the dedicated Core workflow. The exact candidate a69860297d7b26dbb688df0daf16a31b42046462 subsequently passed the dedicated Core run 39982269326, job 120512326423: Xcode 16.4 / iPhoneOS 18.5 ARM64 compilation, 34 real SDK syntax checks, ABI 30/export checks, and the static passive-dlopen gate. The latter is an ARM64 direct-call reachability check, not a runtime load on an iPhone. Actual configured PPU 8f9b154eb34feabb and SPU 7c226c2359020e20 code-generation identities are unchanged. No FPS gain, successful physical restoration, new IPA or physical-device validation is claimed by these host checks.

## Implemented production changes

### Speculative pipeline strides agree with fresh draw-time bindings

`PipelineConverter` incorrectly tested the Vulkan vertex binding index against
the number of guest buffers, excluding the final real buffer because binding
zero is synthetic. It also allowed scalar alignment zero to turn an otherwise
valid stride into zero during conversion. The converter now checks the raw
buffer index and starts from effective minimum alignment one.

The full production Vulkan converter/state/key fixture covers 5,766 states and
88,788 checks per variant. Against the independent fresh-binding stride
oracle, 1,200 divergent keys/cache misses become zero. For example, guest
stride 7 with a 32-bit attribute converts to 8, previously 0. The draw path,
formats, topology and key equality/hash are unchanged. Historically retained
alignment on a buffer that becomes unused is outside this parity claim.

### No closure allocations in render-pass attachment checks

`RenderPassHolder.ContainsAttachment` and `AddForcedFence` now search with
indexed loops instead of captured LINQ predicates. Identity, ordering,
first-match behavior and the first fence's flags remain the same. The complete
class passes 500 scenarios and 22,464 assertions per variant, with equal
functional digests. Each of four 100,000-query allocation probes changes from
8,800,000 bytes to zero (88 to zero bytes per query). GPU resources and dispatch
are doubled; no Vulkan entry point executes in this fixture.

### Queue keys do not allocate shader-stage storage

`GetInitialGraphicsPipelineKey` now uses the same conversion/defaults without
allocating shader-stage storage, which this key-only path never reads. It is
called when registering and retiring speculative pipeline work under the cache
lock. Actual compilation and `Clone` keep the default allocation behavior; no
persistent key cache or extra retained state is added.

The complete Vulkan assembly executes both original and candidate key methods.
All 1,485 compared states/stages have exactly equal keys and hashes, and the
5,766-state stride corpus still passes in the same assembly. Across 20,000 key
lookups, managed allocations change from 640,000 to zero bytes and actual host
native allocations from 20,000 to zero (4.8 MB cumulative allocation traffic,
not resident RAM). Actual stage allocation/free and clone ownership remain
covered separately. No graphics driver or real shader compilation executes.

### Scalar threaded bindings capture a reference directly

The three texture/sampler/image array commands capture a single reference in
the FIFO table when the caller supplies an array of length one. This preserves
the producer-time snapshot while avoiding a new array for each update. The
consumer borrows a per-resource/category one-element array only during its
synchronous backend call; the scratch slot is detached for reentrancy and
cleared in `finally`. Empty and multi-element arrays retain their existing
snapshot behavior. Full hashes of all four reviewed Vulkan/OpenGL consumers
guard the synchronous non-retention contract.

For each of the three paths, 20,000 warm scalar updates allocate 640,000 bytes
before and zero after. Length-zero and length-two allocations are unchanged.
The functional digest is identical, including delayed execution, producer
mutation, FIFO wrap, exceptions and reentrancy. Four backend drift controls are
rejected before GAL edits. The real command helper reports the same maximum
77-byte payload and 80-byte aligned ring stride before and after; these commands
grow from 12 to 20 bytes but do not enlarge the command ring. At most one empty
scratch array remains per resource/category after use; this is a bounded
retention tradeoff, not a measured whole-process RAM saving.

### Modified-buffer snapshots return on every exit

`BufferModifiedRangeList` now returns its private rented arrays on the
current/future-sync early exit as well as after callbacks or fence failures.
Returns clear their object references. The source locks are released in
`finally`; callbacks still run at their original lock boundaries. Inheritance
keeps its private snapshot because callbacks can mutate the range graph.

`BufferMigration` also releases its active traversal count in `finally`. A
throwing migrated flush previously left that count positive, making disposal
spin indefinitely. The new test verifies count zero, completed disposal and
the original source buffer reference count after the failure.

The complete production range/search/migration classes have the same semantic
digest in control and candidate. A real ArrayPool probe over 20,000 checks of
one current-sync range allocates 3,040,000 bytes before and zero after. A separate
instrumented ownership probe returns all 1,715 rentals and leaves no non-null
pooled entries in the candidate. Its retained-entry count is an instrumented
history, not a count of simultaneously retained references in the real pool.
The timing/allocation probe does not measure large-snapshot clearing, flush
throughput, resident memory or iPhone gameplay.

### Render-target snapshots do not root unused textures

`SetRenderTargetsCommand` returns its rented colors array cleared from a
`finally`, including failed conversion/backend calls. Ordering, nulls, aliases,
reference consumption and exception identity remain unchanged. The complete
production command/TableRef test demonstrates that a resource rooted by the
original pool can be collected with the fix. Both variants allocate zero bytes
over 50,000 warm commands. This is a resource lifetime correction, not a
new zero-allocation speedup or an iPhone memory measurement.

## Verification and limits

The receipts and composition record are in
`evidence/melonx-gpu-runtime-20261029/`. They bind source/test hashes and record
the simulated boundaries. Existing successful suites are not replayed for
unchanged CPU, audio, ABI, kernel or texture-conversion paths. The complete
managed Release library is type-checked on Linux with SDK 10.0.100 and existing
cached dependencies; that is not an Apple NativeAOT or physical-device test.
The initial complete build succeeds in 97.54 seconds with 27 pre-existing
warnings and zero errors; the final affected-project build after the key-only
change succeeds in 12.36 seconds with 23 warnings and zero errors. Its 4,965
source/resource inputs match a fresh preparation exactly. The warning counts
are not directly comparable because the second build reuses unchanged projects.

The six pending product questions are the iPhone FPS/frametime result, real
allocation/GC reduction, long-session memory behavior, rendering compatibility,
audio under load and Persona 4 behavior. None is inferred from these host
microbenchmarks. The existing fixed Core85 Apple contract intentionally rejects
changed preparation inputs; a later authorized Core build needs a new contract
covering these changed paths while reusing authenticated unchanged results.

Next optimization priorities are the remaining historical pipeline-key
divergences and multi-element descriptor snapshots, followed by virtual-buffer
readback copies. Their actual frequency and benefit in the same Hogwarts/Persona
scenes must guide the next implementation. No quality reduction, arbitrary
primitive-restart override, additional RAM entitlement, forced collection or
new telemetry is included.

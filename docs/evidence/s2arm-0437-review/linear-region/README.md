# Écritures partielles CPU des textures 2D linéaires

Cette expérience porte sur la fonction WriteTexels du moteur. Les pointeurs, formats, vues et contenus utilisés sont synthétiques. La comparaison prend 0450 comme référence correcte. Les deux patchs livrés sont appliqués tels quels à une copie temporaire. Si le moteur contient déjà l’un d’eux, la fixture le reconnaît, l’inverse dans cette copie et vérifie l’empreinte du bloc d’origine. Une source différente arrête le contrôle avant compilation. Chaque candidat extrait doit aussi correspondre octet pour octet à l’application de son patch retenu. Une troisième compilation retire uniquement la reconnaissance du bit 0x40 dans nvn_deswizzle_geom_ex pour reproduire le comportement initial. Le témoin A/A recompile indépendamment le code de 0450.

## Équivalence

Le stockage d’un pool ordinaire vient du constructeur. Celui d’une texture vient de ce pool et de son décalage. Le chemin WriteTexels ne possède aucune garantie générale d’unicité du stockage. Deux adresses virtuelles différentes peuvent désigner la même mémoire. Les tests utilisent plusieurs mappings partagés du même fichier anonyme temporaire. Ils couvrent également une texture dans laquelle plusieurs pages virtuelles désignent la même page physique.

Le candidat de copie directe échoue sur quatre scénarios de mappings. Le candidat qui capture toutes les lignes source puis n’écrit que la région échoue sur quatre scénarios où une ligne ultérieure, intacte, partage la page déjà écrite. La référence y restitue le contenu d’origine lorsqu’elle encode la ligne ultérieure.

Les deux correctifs proposés capturent d’abord la région source et écrivent ensuite ligne par ligne. Le candidat safe accepte une mise à jour partielle lorsque la taille de tout le niveau est au plus celle d’une page de la machine obtenue par getpagesize(), ou lorsque la région couvre un suffixe complet. Le candidat suffix retient uniquement les suffixes. Pour un suffixe, chaque ligne utile complète doit également tenir dans la longueur d’une page. Cela empêche deux octets d’une même ligne de désigner le même octet physique. Cette condition protège l’ordre des écritures à l’intérieur du memcpy de la référence. La preuve repose sur la granularité de mapping de la VM hôte et reste valable si la zone franchit une limite de page. Dans tout intervalle dont la longueur est au plus celle d’une page, les décalages modulo la taille de page sont uniques.

La copie conserve les deux préparations de la totalité du stockage et la notification finale. Elle utilise 512 octets de pile pour les petites régions, puis une allocation de la taille exacte de la région. Une allocation refusée emprunte le chemin 0450. Les mips, tableaux, vues hors niveau ou couche zéro, cibles 3D, multisampling, régions sortantes ou non alignées sur leurs blocs, pas de source trop courts, niveaux complets et géométries non démontrées reprennent l’implémentation existante. La fixture de refus par bornes vérifie uniquement le refus du chemin accéléré pour les arguments qui dépassent le domaine de l’ancienne API.

Les 3 024 cas indépendants couvrent R8, RGBA8, BC1 et ASTC, les bits 0x10, 0x40 et 0x50, régions intérieures, bords de blocs partiels, alignements et remplissages variés. L’oracle construit séparément tout le niveau logique puis rejoue l’écriture ligne par ligne dans la mémoire de destination et compare l’allocation complète. La fixture d’alias comprend 16 situations, six refus de ligne plus large qu’une page dans un stockage à pages répétées, ainsi que 63 petites textures traversant deux mappings d’une même page. ASan et UBSan vérifient ces expériences. Les sorties brutes contiennent les refus, les contre-exemples et les résultats du contrôle de l’échec d’allocation.

## Reproduction

Sur macOS arm64 ou Linux x86-64, avec Git, Clang et Python 3, fournir l’arbre du moteur du manifeste. Les sources extraites sont le bloc réel WriteTexels, l’implémentation complète nvn_deswizzle.c et le code des formats dans nvn_tex.c. Seuls les appels de suivi de session, de préparation de la plage et de publication de la modification sont remplacés par des compteurs. Un fichier reproduisant le chemin initial et un fichier 0450 sont générés pour les essais.

```sh
python3 run.py /chemin/arbre-moteur sortie
python3 analyze.py sortie > sortie/comparaison.csv
```

Sur Linux, le banc épingle le processus sur un CPU. Sur macOS, il utilise les décisions de placement de l’ordonnanceur. Dans les deux cas il utilise CLOCK_THREAD_CPUTIME_ID et mesure le temps du thread. Chaque cas passe par une chauffe et douze groupes appariés de cinq variantes dans un ordre déterministe mélangé. La deuxième édition de liens inverse l’ordre des objets. À chaud, chaque mesure agrège les appels répétés selon la taille. À froid, CLFLUSH et MFENCE évacuent les données d’entrée et de destination avant un seul appel sur x86. Sur arm64, le témoin parcourt 128 Mio de mémoire avant chaque appel et inscrit cache_pressure_128MiB dans le journal. L’état réel de chaque ligne de cache reste inconnu dans cette dernière mesure. Les métadonnées d’allocateur et le code restent résidents. Le CSV fournit les temps bruts, le nombre et la taille demandée des allocations temporaires, les préparations et notifications, et l’empreinte de toute l’allocation. Les octets temporairement demandés quantifient une allocation, pas le RSS. Les ratios sont calculés paire par paire. Les troisième et dixième rangs sur douze sont fournis pour apprécier leur dispersion.

Aucune IPA, exécution Metal, mesure d’iPhone ou trace de jeu ne fait partie de cette expérience. La fréquence d’appel de ces chemins dans un jeu, l’énergie, la température et la mémoire résidente sur appareil restent à mesurer.

# Connexion de Smash Ultimate à Nextendo sur l’IPA 785

La session du 18 novembre a chargé `01006a800016e000` en version `13.0.5`, acceptée dans le catalogue signé. Le pont a accepté la configuration Nextendo de cette session et le cœur a servi ses données BCAT.

À 07:45:06, 07:45:15 et 07:45:20, heure de Paris, le cœur a refusé le certificat présenté pour `g23380901-lp1.s.n.srv.nintendo.net`. Son sujet et son émetteur étaient tous deux `CN=nintendo-private-server`. Les trois échecs arrivent avant l’authentification NEX. L’enregistrement de 08:43 montre deux ouvertures de « Connexion à Internet… », suivies du retour au menu principal.

Ce nom est celui que Nextendo publie pour Smash. Son guide demande la validation du nom d’hôte et d’une chaîne vers une racine Nextendo publiée. Le certificat présenté ne valide pas dans la session observée. Les anciens journaux ne permettent pas d’identifier la provenance de l’adresse choisie pour cette tentative. [Guide d’intégration Nextendo](https://wiki.nextendo.network/integration#ig-tls)

RewindBox choisit désormais les adresses issues du DNS officiel en priorité. Une adresse intégrée à la compilation sert de repli si le nom n’a jamais été résolu. Le journal de lancement indique l’origine des deux adresses sans publier leurs valeurs. Un essai sur iPhone reste nécessaire pour vérifier le certificat présenté après ce changement et l’accès effectif à la recherche d’adversaires.

## Port sécurisé 60005 — journaux de l'IPA 801, 20 novembre

- Journaux privés `app_1.log` (SHA-256 `ca7eb1f5…`), `MeloNX-core.log` et `MeloNX-launch.log`. Application 0.0.8 (801), Core `bde1a21ccfab`.
- À 15 h 21, heure de Paris, les adresses viennent du DNS (`game=dns nat=dns`), le compte est préparé (`version=13.0.5; catalog=yes; BCAT=4 files`) et la connexion TLS SSBU sur le port 443 se termine en mode compatibilité. Des données sont échangées : jusqu'à 1 033 octets lus et 2 953 écrits. Le correctif de lecture de la 801 fonctionne donc.
- Le jeu ouvre ensuite une connexion TLS vers le port 60005 du même serveur. Le moteur la refuse à chaque essai (`certificate refused for '<adresse IP>' (reason: hostname)`, `AuthenticationException`). Il y a quatre essais en 30 s, puis le retour au menu.
- Cause dans le code : sur ce port, le jeu nomme le serveur par l'adresse IP que le serveur de connexion Smash lui a donnée. Or l'exception consentie exigeait le nom du serveur de connexion. Elle visait pourtant déjà le port 60005, mais elle ne pouvait jamais s'appliquer à cette connexion. Le nom étant contrôlé avant la chaîne, le journal ne dit pas encore quel certificat présente le port 60005.
- Correction (`EmbeddedOnline.cs`). Elle concerne seulement le port 60005 et seulement l'adresse de jeu de la session. Elle s'applique uniquement quand le nom TLS est exactement l'adresse de la socket et que le serveur de connexion Smash a déjà été atteint dans cette session (vérifié ou par consentement).
  - Un certificat qui chaîne vers les racines publiées par Nextendo est accepté comme vérifié.
  - Le certificat privé générique est accepté seulement avec le consentement SSBU déjà en place.
  - Un refus sur ce port indique maintenant `legacy-private-certificate=yes/no` et l'état de la connexion au serveur de connexion. Aucune donnée de certificat n'est journalisée.
  - Les autres jeux, les autres ports, le NAT et les adresses manuelles ne changent pas.
- Vérification : contrat Core existant réussi (523 contrôles). Aucun SDK .NET n'est disponible dans cet environnement : la compilation de contrôle est celle du Core sur macOS. Rien n'est encore validé sur iPhone : connexion NEX, NAT et recherche d'adversaires restent à observer.

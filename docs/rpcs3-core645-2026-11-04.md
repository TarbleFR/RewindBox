## Défaut, dans le vrai code

Quand un port n'est pas écrit à temps (2 périodes si aucun port n'est écrit, 4 périodes, soit 21 ms, si un seul manque),
`cell_audio_thread::operator()` fixe `untouched_expected` puis appelle `advance()` **sans rien mixer ni mettre en file**.
Deux conséquences :

1. le PCM des ports déjà écrits pour cette période est perdu (5,3 ms), ce qui crée une discontinuité ;
2. l'anneau de sortie, de 34 ms, perd un bloc ; en rafale, il se vide et le contrôleur de reprise iOS ajoute 21 à 100 ms
   de silence.

Or `advance()` remet à zéro et retague le bloc courant de chaque port (`reset_ports(0)`) : un port non écrit se mixe donc
en silence. Le matériel PS3 mixe ce qui se trouve dans les blocs à chaque période.

## Correction

Sur iOS, à l'expiration, la boucle repasse une fois avec les ports non écrits attendus. Les chemins existants font alors
le travail :

- ils mixent les ports écrits (les autres sont silencieux) ;
- ils mettent en file le bloc silencieux si aucun port n'est écrit ;
- ils notent un bloc manquant si l'étirement temporel est actif, sans y injecter de zéros ;
- puis ils appellent `advance()` comme avant.

Sont inchangés : les périodes invitées, les événements MIX, les délais d'attente, la taille du tampon, le tempo et le
contrôleur de reprise. `disable_sampling_skip` garde le chemin amont.

## Vérifications

`test/rpcs3_audio_timeout_mix645_test.py` extrait le vrai bloc de décision des deux arbres, de `enqueued_samples` jusqu'au
compteur `incomplete_mixes`, période dynamique comprise. Il les compile avec le vrai contrôleur de reprise
(`IOSAudioRecovery.h`), qui lit l'anneau au rythme de RemoteIO.

- **Cas unitaires :**
  - expiration partielle : le contrôle jette le port écrit, le candidat le mixe ;
  - expiration totale : le contrôle ne produit rien, le candidat met en file un bloc silencieux ;
  - étirement actif : le candidat note un bloc manquant ;
  - `disable_sampling_skip` et cas normal : comportement identique.
- **Modèle de rafale** (producteur synthétique, plus sévère que les journaux) :

  | | Contrôle | Candidat |
  | --- | --- | --- |
  | Blocs de ports écrits jetés | 803 | 0 |
  | Discontinuités | 1 621 | 839 |
  | Trames de remplissage | 384 256 | 198 144 |
  | Silence de reprise | 170 496 | 73 216 |
  | Reprises | 100 | 51 |

- **Synchronisation A/V :** la latence de l'anneau reste bornée par sa capacité (moyenne 23,1 contre 24,0 ms, maximum
  42,7 ms dans les deux cas). Les périodes invitées diffèrent de moins de 1 %. La fenêtre propre est strictement identique.
- `test/rpcs3_core645_test.py` : incrément authentifié et réversible vers le Core 641, puis la suite du Core 641 sur l'arbre inversé.
- `test/rpcs3_core645_codegen_test.py` : identités codegen inchangées. La clôture source de la route est validée.

## Limites et mesures iPhone

- **Synchronisation et silences.** La synchronisation A/V reste bornée par la latence de l'anneau, qui ne change pas. Les
  blocs remplacés sont silencieux pour le seul port en retard : ce n'est pas un time-stretch.
- **Manque résiduel.** Il vient du producteur invité, qui écrit en rafales liées aux frames (40 à 50 ms) alors que le
  tampon n'en garde que 34 ms. Test décisif sur iPhone, sans nouvelle build : même scène AC, réglage existant « Audio
  buffer duration » 34 ms puis 64 ms. Pour chacun, relever les deltas `AUDIO641` (manques, `advances_without_mix`,
  `filler_frames`) et noter à l'oreille l'écart labiale/son. Aucun réglage n'est changé par défaut.
- **Aucun gain audio annoncé** sans les deltas `AUDIO641` d'une session AC comparable sur le Core 645.

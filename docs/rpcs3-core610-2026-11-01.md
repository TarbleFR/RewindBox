## Nouvelles lignes de journal (journaux existants uniquement)

- `COREPROF EXITSPAWN phase=request|stop_main|boot_begin|boot_return`,
  `COREPROF SHADERWARMUP phase=begin|end`, `COREPROF RUNPPU phase=dispatch|running`,
  `COREPROF FIRSTFLIP` et `Vulkan driver pipeline cache: save started|returned|skipped`.
  Ces lignes séparent les sept phases d'une transition SELF, par exemple le passage de BO2
  au multijoueur.
- `COREPROF FEEDBACK610`, une ligne par fenêtre de performance, juste après `RSXFRAME551` :
  - `draw_renderpasses` ;
  - `snapshot_draws`, `snapshot_copies`, `duplicate_copies`, `snapshot_mpix` ;
  - `pb_draws` ;
  - `msaa_feedback_reads` et `depth_feedback_reads`.
  
  Pour obtenir les valeurs par image, diviser par `frames=` de `RSXFRAME551`. Le temps GPU
  n'est toujours pas mesuré.
  
  **Limite de `draw_renderpasses` (relevée après la compilation du Core 610).**
  `VKGSRender::begin_render_pass()` est appelé à chaque draw, même lorsque
  `vk::begin_renderpass` sort tôt parce que la passe est déjà ouverte. Ce champ vaut donc à
  peu près le nombre de draws. Il ne mesure pas les vraies ruptures de passe Metal dues aux
  snapshots. Tous les autres champs restent exacts. La correction, qui consiste à compter
  dans `vk::begin_renderpass` uniquement quand une passe démarre réellement, est prévue pour
  le lot suivant.

## Correctif hôte NeoSwap de l'IPA 610 (hors Core)

Avant chaque démarrage RPCS3, `Rpcs3InternalService.launchTitle` demande au plugin NeoSwap
de préparer le relais de pages invitées (`prepareGuestRelay`).
- Le pont n'attendait le relais qu'au chargement du Core, une seule fois par processus.
- Après une session, le relais s'arrête quand il est inactif.
- Lors d'une relance ou d'un changement de jeu, les blocs invités préalloués (environ
  768 Mio) étaient donc mappés hors relais pour toute la session.

L'attente se fait hors du fil principal :
- elle est bornée à 10 s côté natif et à 12 s côté Dart ;
- elle est journalisée (`guest_relay_prepare` dans NeoSwap-v1.jsonl, et une ligne Flutter
  `RPCS3 guest relay before boot`) ;
- elle ne fait jamais échouer le lancement ;
- elle est compilée uniquement avec `NEOSWAP_RELAY`.

Le pont RPCS3, verrouillé par empreinte, n'est pas modifié.

Une revue contradictoire de ce correctif a confirmé trois défauts, corrigés avant la
livraison dans `NeoSwapRelayService.mm` :
- **Relais encore prêt d'une session précédente.** La maintenance d'inactivité pouvait
  l'arrêter entre la réponse et le début de la nouvelle session. La préparation passe
  désormais par `NeoSwapRelay_PrepareForBoot`. Si le relais est prêt et qu'aucune session
  RPCS3 n'est active, elle efface l'observation de session, comme le fait un démarrage
  neuf, et la maintenance revérifie ce drapeau dans la section critique qui arrête le
  relais. Le relais est donc conservé jusqu'à ce que la nouvelle session soit observée.
- **Attente active sous pression mémoire.** Une relance refusée par `start` (pression
  mémoire) faisait tourner `waitReady` jusqu'à l'échéance. L'attente ne relance plus
  qu'une seule fois, ce qui équivaut à l'ancien comportement puisque
  `kMaxFastFootprintRetries = 1`. La pression efface aussi la relance rapide en attente,
  et l'attente rend `NEOSWAP_RELAY_PRESSURE`.
- **Démarrage du relais par le plugin.** Le plugin appelait directement le démarrage du
  relais, alors que le contrat de cycle de vie en réserve la propriété au service (test
  `test_ipa_validator_matches_single_relay_lifecycle_ownership`, de nouveau vert). Le
  plugin n'appelle plus que la préparation.

L'enregistrement du journal précède toujours la réponse à Dart, donc le démarrage. Les
tests Dart (9) éliminent 7 mutants. Le code Objective-C++ n'est compilé que par la
livraison sur macOS. Aucun essai sur iPhone n'a encore été fait.

## Limites

- Aucune de ces corrections n'a été observée sur iPhone. Aucun gain de FPS n'est revendiqué.
- Rien ne relie encore la correction LR au gel de l'introduction de GOW3. Aucune trace
  appareil ne montre de SPU armé bloqué.
- La réduction du scintillement d'AC par l'invariance de position reste une hypothèse.
  D'autres causes restent possibles : mélange programmable, MSAA, profondeur ou ZCULL. Le
  recensement est là pour les départager.
- Le passage de DW6 en LLVM est un essai à une seule variable. S'il échoue, `CONFIG_LAYERS`
  et `JITPROF_BOOT` montreront à quelle étape.

# PlayStation 3 RetroAchievements through the embedded RPCS3 Core (1 November 2026)

**Status:** source only, on branch `Claude`, on top of the Core 610 source lot
(`fefad81d`, canonical patch `a63b9643`). No Core, IPA or CI build was run.
Nothing was tested on an iPhone. The Core part is **staged**: it is not in the
canonical delta (see [Core hooks](#core-hooks-staged-not-built)). These
changes are not part of IPA 610: its recipe reviews its product scope against
609 (RA credentials fix, Core 610, Dart profiles).

Marker: `NEOSTATION_RPCS3_RETROACHIEVEMENTS_V1`.

## What RetroAchievements offers for PS3 today

RetroAchievements already defines the console (`RC_CONSOLE_PLAYSTATION_3 = 82`)
in the pinned rcheevos v12.5.0: hashing (PARAM.SFO + EBOOT.BIN, from an ISO or
an extracted folder) and a 4-region memory map whose addresses are PS3 guest
virtual addresses. On 1 November 2026 the public API returned, for console 82:
1,422 listed games, **0 games with an official achievement set** and 2 known
hashes, both linked to games without achievements (The Last of Us, Rogue
Legacy). So, even after a Core build, the most common in-game results will be
"game not recognized" (unlisted hash) or "recognized, nothing to track" until
RetroAchievements publishes PS3 sets. RetroAchievements has no reference PS3
emulator integration to compare against.

## Device report of 2 November 2026: "Jeu non reconnu" for Black Ops II, Assassin's Creed, Bladestorm

The in-game status said "Jeu non reconnu par RetroAchievements (version ou dump
non référencés)" for these three titles. This is RetroAchievements' real answer,
not a hashing defect of the app: on 2 November 2026 the public client endpoints
returned, for console 82, **2 known hashes in all** (`r=hashlibrary&c=82`: The
Last of Us 41360 and Rogue Legacy 42091) and 1,446 listed titles
(`r=gameslist&c=82`), among them Assassin's Creed (41323), Call of Duty: Black
Ops II (41878), Bladestorm: The Hundred Years' War (42421) and Bladestorm:
Nightmare (41718), none with a linked hash. Whatever the dump, rcheevos gets
game id 0 (`RC_NO_GAME_LOADED`) until RetroAchievements links a disc hash, and
no PS3 title has a published achievement set yet (1 November survey above).
Requests: hash library and title list only, no account, no key.

Changes:

- The PS3 status no longer blames the dump: an unknown hash under RPCS3 shows
  `unknownGamePs3` ("Ce jeu PS3 n’est pas (encore) référencé par
  RetroAchievements : aucun succès à suivre", 12 locales); other engines keep
  `unknownGame`.
- Unreadable files are told apart: `RC_INVALID_STATE` (rcheevos "hash generation
  failed") and a missing PARAM.SFO/EBOOT.BIN layout now end with
  `RA_GAME_HASH_FAILED` (`hashFailed`: "Jeu non identifié : ses fichiers n’ont
  pas pu être lus pour RetroAchievements") instead of "not recognized".
- The PS3 journal (`Diagnostics/PS3/RPCS3-diagnostic.log`) records the hash that
  RetroAchievements did not know: `ra.game load_failed result=-29
  unknown_hash=<md5>` (lowercase MD5 of PARAM.SFO + EBOOT.BIN, checked before it
  is written; never a path or account data). It is what a set must list for this

Delivery note: `Rpcs3Achievements.mm` is an inherited deferred path (its

that reviews this change must first promote `b06888a9` for that path, or keep

## Architecture

| Layer | Role |
| --- | --- |
| Core (staged patch) | Optional exports: VBlank frame callback, guarded guest reads, session info. No account, network, hash or policy. |
| `Rpcs3Achievements` (host, new) | rcheevos client for one launch: token sign-in, identification, frame evaluation, unlock events, Hardcore decision, state publication. |
| `Rpcs3InternalBridgePlugin` | Takes the central launch ticket, starts/suspends/resets/ends the client, Hardcore gates in the session menu, toasts. |
| `retro_achievements_session` (central) | Unchanged account/Keychain model; now accepts RPCS3 (MeloNX stays unsupported). |
| Dart | `RetroAchievementsCapabilities` supports `rpcs3`/`ps3`; `Rpcs3InternalService.launchTitle` prepares one ticket and releases it on failure. |

### Core hooks (staged, not built)

`build-utils/rpcs3/retroachievements-core.patch` (manifest
`retroachievements-core.json`) is a purely additive delta over the Core 610
canonical postimage (5 files, 381 added lines, none removed). It was first
written on the previous postimage (`70d694bb`) and re-applied unchanged after
Core 610 modified `RSXThread.cpp` (one include line moved the anchor) and
`RPCS3IOS.cpp`. Before the fold for Core 611, `copy_text()` was guarded so an
empty view's null `data()` never reaches `memcpy` (GCC ASan/UBSan finding on
`copy_text(..., {})`; behaviour unchanged; the new header went from 210 to 215
lines, patch `518dc4a0…`):

- `rpcs3/ios/RPCS3IOSAchievements.h` (new, standard C++ only): frame hook,
  page-wise guarded reads, Hardcore speed rule, boot record.
- `rpcs3/ios/RPCS3IOS.h`, `RPCS3IOS.cpp`, `RPCS3IOS.exports`:
  `rpcs3_ios_ra_api_version` (1), `rpcs3_ios_ra_set_frame_callback`,
  `rpcs3_ios_ra_read_memory`, `rpcs3_ios_ra_get_session_info`.
  `RPCS3_IOS_ABI_VERSION` stays **30**; no earlier export changes.
- `rpcs3/Emu/RSX/RSXThread.cpp`: one call after the guest VBlank event in
  `rsx::thread::post_vblank_event`, under `RPCS3_IOS`.

Behaviour:

- **Frame.** The callback runs on the RSX VBlank thread (60 Hz). That thread
  starts only once the game initialized RSX (after the PPU compilation of a
  first boot), waits while emulation is paused and is joined before the guest
  memory is released. With no session attached it costs one atomic load; with
  one, `try_lock`: a VBlank never waits for the host.
- **Memory.** `vm::try_access` page by page (4 KiB, the same guarded path as
  RPCS3's debugger); unmapped or protected pages are zero-filled; only while a
  game runs or is paused; never a write; exceptions contained.
- **Session info.** Effective `Vblank Rate`, `Clocks scale`, `Frame limit`
  (Hardcore-compatible only at 60 Hz, 100 %, bounded limit) and the library
  entry of the last `rpcs3_ios_boot_game`: the base ISO or game directory,
  never an installed update or a savestate file.
- No hook takes `g_api_mutex` (held for seconds by a boot or stop) or writes
  `last_error`.

**Why it is not folded into `embedded-core.patch` yet.** Every IPA workflow
(for example `ios-ci.yml`, "Verify and install passive RPCS3 Core") requires
`canonical-source.json`, `embedded-core.patch` and `Rpcs3CoreABI.h` to equal
the commit of the prebuilt Core it installs. Folding the hooks now would block
every IPA, including the pending credentials fix, until a new Core is built.
`build-utils/rpcs3/fold_retroachievements_core_patch.py` performs the fold as
the first step of an authorized Core build (validated in a throwaway copy: the
folded delta re-materializes on a pristine upstream clone with every postimage
hash verified).

### Host client

- **Ticket and account.** `RBRATakeLaunchConfiguration(args, "rpcs3")` once per
  launch; credentials come only from that snapshot (Keychain token). Every exit
  path ends it (`RBRAEndSession`); Dart also releases an unconsumed ticket.
- **Without the Core hooks** (current prebuilt Core): the client publishes
  `RA_CORE_UNSUPPORTED` → in-game status "not available for this game or
  emulator core". The game is unaffected.
- **Identification.** The client hashes the Core-reported base entry the way
  rcheevos expects: `disc.iso` directly, else `PS3_GAME/USRDIR/EBOOT.BIN`, else
  `USRDIR/EBOOT.BIN`. Hashing runs on the client queue, never on a game thread.
- **Threads.** Frames are evaluated on the VBlank thread with `try_lock` on the
  client (skipped while sign-in, hashing or a server answer holds it). Server
  answers, idle pings (1 s, only when no frame was evaluated), resets and
  destruction run on a private serial queue. Background memory reads are off.
  Registration and detachment of the frame hook are serialized with shutdown.
- **Reads.** RetroAchievements PS3 addresses are guest virtual addresses
  (identity). A zero-filled page is reported as read: PS3 titles allocate
  memory at run time, and a short read would make rcheevos disable every
  achievement using that address for the whole session.
- **Restarts.** A settings change or a savestate load stops and boots the title
  again: frames are suspended first, then `rc_client_reset` runs before
  evaluation resumes. A refused stop resumes the same run without reset. Saving
  a state (which the Core restores in place) needs no reset.
- **Status.** The central launch status is attached at the first VBlank, so a
  long first-boot compilation never shows "tracking not confirmed". A client
  that ends before its hook is attached signals it at once.
- **Unlocks.** Title, description and localized points (`RBRAPointsText`) on
  the shared FIFO toast (kind 1), with the existing translation. Status toasts
  use kind 3.
- **Diagnostics.** RPCS3 journal events `ra.hardcore`, `ra.login`, `ra.identify`
  (source kind only), `ra.game`, `ra.active`, `ra.unlock`, `ra.restart`,
  `ra.failed`, `ra.session_end`, `achievements.status`,
  `achievements.unlock_presented`. No username, token, URL, body or file path.

### Hardcore

Hardcore is **applied** only if the player asked for it and none of these hold;
otherwise the session runs in Softcore and the status shows
"Hardcore not applied" (achievements still count):

| Condition | Applied at |
| --- | --- |
| Launch from a savestate | start |
| Any enabled patch/cheat for the title (any PPU hash, installed revision) | start, after a restart |
| VBlank ≠ 60 Hz, clocks ≠ 100 %, or frame limit Off/120/Infinite | start, after a restart |

While Hardcore is applied or pending (sign-in, identification):

- loading a state from the menu is refused with "Unavailable in Hardcore mode"
  (12 languages, central `RBRALocalizedText`); saving stays available;
- cheats cannot be enabled (the shared cheat list disables its toggles and
  shows the same notice); disabling remains possible;
- a restart that would bring cheats, a savestate or a speed change ends
  Hardcore for the session (never re-enabled mid-game).

A terminal failure (unknown game, refused token, no achievements…) lifts every
restriction.

1. Fold the hooks: `python3 -B build-utils/materialize_rpcs3_core.py <tree>`,
   then `python3 build-utils/rpcs3/fold_retroachievements_core_patch.py <tree>`;
   commit the regenerated delta, manifest and pin.
2. Build the RPCS3 Core from that delta, then an IPA that installs it.
3. On iPhone: a PS3 title with RA on (expect "not recognized" or "nothing to
   track" today), Hardcore gates, quit/settings/savestate restarts, and the
   journal events above. Real unlocks need a published PS3 set.

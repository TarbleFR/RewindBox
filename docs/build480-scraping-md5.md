# Build 480 — bounded scraping file hashing

The maintainer authorizes a private IPA correcting the scraper's native-file MD5 fallback on Claude. The supplied application journal repeats the sequence metadata scraping → ScreenScraper ROM-not-found response → next app startup five times. The video shows one worker and zero completed games. The first game's temporary ISO copy is 3,363,110,912 bytes. This matches an actual source defect: the fallback reads the complete file into RAM before hashing. The journal does not identify the exact termination mechanism on the iPhone 15 Pro Max.

Native files now feed the complete MD5 converter as a stream. No game bytes or hashing scheme change. Specialized console digests and the Android SAF provider contract are preserved. The existing background isolate remains; the caller's initialized logger persists `[ScrapingMD5] start`, `completed` and `failed` with basename, byte count and elapsed time. No user-facing strings or engine settings change.

The focused proof runs the original production method under an I/O guard that rejects whole-file reads without allocating a multi-gigabyte buffer. The new production method must pass that guard, empty and boundary vectors, six concurrent worker hashes and success/failure app.log checks. An actual sparse 3,363,110,912-byte fixture has nonzero markers across 64 KiB, above 2 GiB and in the final byte. Its independent Python hashlib MD5 is `f70f295bdaa27ba3e3ebc9f6fce9ddb8`. The real background hasher must produce that complete digest with less than 192 MiB additional sampled process RSS. This host measurement is not a physical iPhone crash reproduction.

All unchanged delivered 479 catalogue, native helper, engine, library and skin inputs reuse exact successful validation. No emulator Core rebuild or public release. One cold device Release is requested; the warm benchmark remains disabled. Build 480 is reserved. Actual source, focused proof and IPA identities will be recorded after they succeed.
